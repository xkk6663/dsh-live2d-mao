### 1.1 三条必须继承的踩坑结论（已全部落地）

## 4. 过程中修掉的两个真实缺陷（Lead 定位）

### 4.1 桌宠流式气泡被 5s 轮询打掉（阻塞 E2E 门禁）

**症状**：`agent_stream` 逐 token 流能正确播完，但 ~600ms 后气泡立刻清空+隐藏，
而不是按设计 hold `max(3500ms, 字数×60ms)`。

**根因（CDP 栈追踪确证）**：`hideSpeechBubble ← applySettings ← pollStatus ← start`。
`applySettings` 里 `if (!settings.live2d_speech_bubble_enabled) hideSpeechBubble()`
**无条件执行**；而 `hideSpeechBubble()` 内部第一件事就是 `cancelAgentStream()`
—— 这正是打断流的直接原因，`finishAgentStream` 的 `holdTimer` 从未有机会生效。

**关键补充（渲染端负责人实测，比初判更准确）**：它**不止每 5s 触发**。
`start()` 里那次 `await pollStatus()` 会在流播放中途回包（实测 t+530ms 与 t+956ms 各命中一次）。
所以即使把 5s 轮询去掉也不够 —— 启动时那次在途轮询同样会打掉流。

**修法（下降沿 + 无活跃流 双守卫）**：
```js
const bubbleEnabledNow = settings.live2d_speech_bubble_enabled !== false
const bubbleJustDisabled = speechBubbleEnabledApplied !== null && speechBubbleEnabledApplied && !bubbleEnabledNow
speechBubbleEnabledApplied = bubbleEnabledNow
if (bubbleJustDisabled && streamState === null) hideSpeechBubble()
```
- **为什么要下降沿**（比"只看 `streamState`"更强）：`pollStatus` 是**在途异步**的，
  `start()` 那次 await 可能在流开始前发出、回包落在流播放中途，此时 `streamState`
  可能恰好为 `null`（上一段流刚收尾）⇒ 单守卫会漏判。
- **`speechBubbleEnabledApplied` 初值必须是 `null` 而非 `true`**：初值 `true` 会让启动时
  在途轮询带回的首个假值被误判成"用户刚关开关"（实测复现的第二个坑）。
- 保留了"用户主动关开关立即隐藏"语义；总开关的**另一条独立闸门**仍在 `applyAgentStream`
  开头（`if (settings.live2d_speech_bubble_enabled === false) return`），新流该挡还是挡。

**Lead 独立复验**（不依赖渲染端自测）：
| 场景 | 结果 |
|---|---|
| 总开关=false 推流 | **被挡住** ✅ |
| 总开关=true 推流 | **正常播完 "甲乙丙"** ✅ |
| 播放中用户关开关 | **立即收尾**（before="甲乙" → after=""）✅ |

### 4.2 E2E 本身耦合真机状态（测试缺陷）

页面会 `GET /api/companion/status` 取真实 settings，而**用户本机
`live2d_speech_bubble_enabled` 恰好是 `false`**（用户自己关的）⇒ [1][2][5] 全挂，
**看起来像产品缺陷，实际是测试耦合了真机状态**，且不可复现（手动打开跑到一半又被翻回去）。

**修法**：harness 加 status 端点桩（只覆盖 settings，其余透传真实后端），并写明原因。

> 这与该 harness 作者已有的纪律一脉相承（其 `[7]` 用例注释：
> "避免把测试造假的载荷当成产品缺陷"）——反过来，**也不能让真机状态把测试变成随机数**。

### 4.3 关于 [2] 用例"偶发失败"的如实记录（留档，供后人判断）

现象：整脚本连续跑时 `[2] 气泡内容被新流替换` 曾约 3/10 失败（拿到第一条流的全文）。

**两种解释并存，未最终定论，如实记录**：
- **Lead 的观察**：正常负载 10 次全过、人为重载（4 job + 12 个满载进程）3 次全过、
  单用例隔离 14 次全过、`[1]→[2]` 复刻 10 次全过 ⇒ 倾向"当时 3 名团队成员各开 Chromium
  并发跑，CPU 竞争导致临界时序抖动"。
- **渲染端负责人的异议（保留）**：其自建探针曾 6/10 复现，并抓到"第二条流零写入"的时间线
  （632ms 停住）⇒ 认为可能是真实竞态。

**当前处置**：按"不引入时序补丁"收尾（**未加 sleep、未改 hold 语义**）。
最终验证为 **连续 3 次 15/15 + guard 全 0**。
**若将来再次复现**，建议优先查 `finishAgentStream` 的 `holdTimer` 回调与
`cancelAgentStream()` 在"两个 `streamState` 对象交替"时的干净性 —— 这是两人都指向的同一处。

> ⚠ 记录一个**反直觉的坑**：把该用例等待从 700ms 放宽到 900ms，
> 会让偶发（30%）变成 **100% 稳定失败** —— 因为 900ms 时第一条流已 finish、
> `holdTimer` 已设好，替换路径反而撞上"已完成态"分支。
> **不能用"加等待"来糊这个问题。**
