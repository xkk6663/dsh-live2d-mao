## 1. Cordis 事件订阅签名（易错点）

**`session/event` 的第一个参数是 session，第二个才是 event**：

```js
ctx.on("session/event", (session, event) => { ... })
```

证据（三处独立代码一致）：
- `dsh-agent-loop/lib/index.js:319` — `ctx.on("session/event", (subject, event) => { if (subject !== session) return; ... })`
- `dsh-agent-loop/lib/index.js:974` — `this.ctx.on("session/event", (session, event) => { if (session === this.session) toolRecovery.observe(event); })`
- `dsh-user-questions/lib/index.js:515` — `ctx.on("session/event", (session, event) => { if (event.type === "user/message") ... })`

要**全局**收全会话（不是仅本插件作用域）时加第三参：

```js
ctx.on("session/event", (session, event) => { ... }, { global: true })
```
证据：`dsh-user-questions/lib/index.js:510,514,524` 用的就是 `{ global: true }`。
**多 session 气泡栈（7.4）必须加 `{ global: true }`**，否则拿不到其它 session 的事件。

## 2. 7.1 逐 token：`agent/assistant-stream`

发射点：`dsh-agent-loop/lib/index.js:1068`

```js
this.dispatch.emit("agent/assistant-stream", { frame });
```

`frame` 的结构由 `AssistantStreamAccumulator`（`dsh-llm/lib/types/assistant-stream.js:31-128`）产出。
**帧是"紧凑记录"（compact record），不是原始 delta**：

| record.type | 字段 | 说明 |
|---|---|---|
| `text-chunks` | `{type,time0,index,dt:[],texts:[]}` | ★ **正文**（我们要的） |
| `reasoning-chunks` | `{type,time0,index,dt:[],texts:[]}` | 推理草稿 —— **必须丢弃，不得进气泡** |
| `tool-call-chunks` | `{type,time0,index,dt:[],id,name?,args:[]}` | 工具参数分片 —— 不属正文 |
| `chunk` | `{type,time,chunk:{...}}` | 原始块（`block-start`/`block-end`/`usage`/`finish`） |
| `block-end` (在 `chunk.chunk` 内) | `{type:'block-end', index, block:{type:'text', text:'...'}}` | ★ **权威全文**，用于零丢字校正 |

**拼接规则**：`dt.length === texts.length - 1`（块间间隔，毫秒）；
第 0 块时间 = `time0`，第 i 块时间 = 前 i 个 `dt` 之和 + `time0`（见 `expandAssistantStream`，:135-168）。

**与现有边车通道的字段对齐**（`dsh_adapter.py::_publish_stream`）——桌宠渲染端已消费这个形状，
插件侧请产出**同样字段**，这样渲染端零改动：

```json
{ "session":"...", "turn":1, "step":1, "seq":12, "index":0,
  "frame":"text-chunks", "time0":1791981757968,
  "dt":[41,0,0,0,0,0,0,0,0,15,15,0,13],
  "texts":["I","'ll"," start"," by"],
  "final_text":"I'll start by", "total_ms":1234 }
```

> ⚠ 交接单 7.1 的验收写"打字机延迟 < 100ms（⚠ 日志通道只能事后回放，真实时必须走 `session/follow`）"。
> **本条要修正**：插件形态下拿到的是 `agent/assistant-stream` **实时事件**（进程内 dispatch，
> 无写盘往返），**天然就是真增量**，比日志通道（p50 215ms）快一个量级。
> 所以 7.1 在插件形态下**不需要** `session/follow`——交接单那句话是针对"日志边车通道"说的，
> 而 M6/M7 已改走插件内事件。**这是插件形态相对现有链路的实质性收益，应记入结论。**

## 3. 7.2 审批应答：`approval/request` waterfall

`dsh-user-approval/lib/index.js:176`（`ApprovalService.decide`）：

```js
const answer = Promise.resolve()
  .then(() => this.ctx.waterfall(
      scopeTarget(req.agent, req.agent),   // ← Agent 作用域
      "approval/request",
      req,                                 // ← 请求对象
      () => Promise.resolve("unavailable") // ← 无应答者时的兜底
  ))
  .then((outcome) => OUTCOMES.includes(outcome) ? outcome : "unavailable",
        () => "unavailable");
```

**outcome 枚举**（:30-35）：
```js
const OUTCOMES = ["allowed-once", "rejected", "cancelled", "unavailable"];
```
- **`allowed-once` 是唯一的"允许"**（:124 原文 "`'allowed-once'` is the only grant"）
- 兜底/异常 → `unavailable`（fail-closed，:176 的两个 catch 分支）

**插件接法**（注册作答者）：
```js
ctx.on("approval/request", (req, next) => {
  // req: { agent, toolName, callId?, reason?, signal? }
  return decideInPet(req)          // → 'allowed-once' | 'rejected'
})
```
> 返回值**必须**落在 `OUTCOMES` 内；返回其它字符串会被规范化成 `unavailable`（=拒绝）。
> 桌面端策略：桌宠弹"允许/拒绝"→ 用户点 → resolve 成 `allowed-once` / `rejected`。
> 用户不点/超时 → 应返回 `cancelled`（或让 signal abort）。

**策略闸门（重要）**：`decide()` 在派发 waterfall **之前**先查有效策略（:175）：
```js
if (this.effectivePolicy(session) === "never") return "rejected";
```
⇒ **本会话当前就是 `never`（审批提示已禁用）**，所以：
- 插件**收不到** `approval/request` waterfall（在 :175 就被短路了）
- 要联调 7.2，必须先把 DSH 的审批策略切回 `ask`
- 这不影响代码正确性，但**影响验收演示**——验收时需在 `ask` 策略下做

## 4. 7.3 提问应答：`ctx.userQuestions.answer`

`dsh-user-questions/lib/index.js:552-588`：

```js
answer(agent, callId, answer)   // → boolean（true = 问题仍是 continued 且回复已入队）
```
- `answer.answers` 形状（:58-66 的 `answerSchema`）：
  ```ts
  { id: string, selected: string[], custom?: string }
  ```
  —— **每个问题一条**，且**必须逐个命名该 call 的每个问题恰好一次**（:560 的校验）
- 校验失败抛 `UserQuestionError`：`BAD_ANSWER` / `REPLY_QUEUED` / `CALLER_NOT_LIVE` / `DELEGATED_CALLER`
- 它把答案作为一条 `user-question-reply` 的用户消息 **steer** 进 agent（:582）
- **只对 `state === "continued"` 的问题有效**（:554 `this.continued(agent).find(...)`）

**只读观测**（给桌宠弹选项用）——同样走 projections：
```js
const view = ctx.sessionProjections.stateOf(session, "userQuestions");
// view.questions.active   → [{ callId, questions:[{id,question,header?,options?[],multiSelect?}], state:'open'|'continued' }]
// view.questions.settled  → [{ callId, answers:[...] }]
```
证据：`dsh-user-questions/lib/index.js:268-292`（projection key `"userQuestions"`，wire view = `state.questions`）。

> 注意 `ask()` 会在 `ctx.waterfall(scopeTarget(agent,agent), "user-questions/request", {...request, agent}, noAnswerer)`
> 上征询作答者（:681-684）。插件若要做"桌宠弹选项"，可注册 `user-questions/request` 作答者；
> 但**回传答案**仍建议走 `ctx.userQuestions.answer(...)`（它带完整的校验与 steer 语义）。
> 兜底是 `NO_PROVIDER` 拒绝（:679）——即没有作答者时 fail-closed。

## 5. 7.4 多 session 气泡栈

- `session/event` **监听全会话**（`{global:true}`），天然能拿到多 session
- 按 `session.id` 分桶即可；上限 `MAX_SESSION_BUBBLES = 12`（技术方案 §2 表）
- 子会话识别：`session.parentSessionId` 存在 / `session.origin === "subagent"` 表示子代理会话
  （证据：`dsh-api-session-controller/lib/typert.host.js:448-450` 的 session 描述字段）
- 现有 `dsh_adapter.py` 用 `delegationDepth=0` 选主会话——插件侧可沿用同样策略

## 7. 给实现的硬性提醒

1. **`session/event` 首参是 session**——写错会静默拿不到事件（最难查的一类 bug）。
2. **全局监听要 `{global:true}`**，否则多 session 气泡栈收不全。
3. **`reasoning-chunks` 一律不外发**——推理草稿进桌宠气泡是明确越界（既有链路同款白名单）。
4. **审批 outcome 必须落在 `OUTCOMES` 枚举内**，否则被规范化成 `unavailable`（=拒绝）。
5. **`stateOf` 可能返回 `undefined`**——兜底后再用。
6. **本会话审批策略是 `never`**——审批 waterfall 在 :175 被短路，联调前需切 `ask`。
7. **D1：不引入 TTS 依赖**；`voice` phase 保留为预留态（无 TTS 源则不触发）。
