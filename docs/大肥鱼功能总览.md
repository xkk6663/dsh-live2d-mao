
三条并列通道，互不阻塞：

| 通道 | 端点 | 用途 |
|---|---|---|
| HTTP | `POST /api/companion/chat` | 一问一答（权威结果） |
| HTTP | `GET /api/companion/chat/history` | 历史（含附件 URL） |
| WS | `ws://…/api/companion/ws` | 流式正文 `agent_stream`、图片 `agent_image`、音频 `agent_audio`、气泡 `agent_bubble` |

## 3. 多模态

### 3.1 她发图（表情包）

```
AstrBot 发 [IMAGE]xxx.png 帧
  → 后端下载字节 → 落盘 pet-data/…/agent_media/<sha16>.ext
  → ① WS 推 agent_image {url, response_id, accent}
  → ② HTTP 响应 attachments 带 url
  → 对话界面 <img src=url>（260px 上限，多张自动换行）
  → 桌宠气泡：图 + 同一轮的那句话，图文并存，3 秒收起
```

> ⚠️ **绝不可把 base64 塞进 WS**：3.6 MB 的图 base64 后约 14 MB，
> 超过 WebSocket **1 MB 单帧上限**，会直接踢掉连接（实测 `sent 1009 message too big`）。
> 后端历史上有一条漏改的旧分支就这么干过，已删除。

### 3.2 她发音频（点歌）

```
「点歌 晴天 1」→ AstrBot 音乐插件发 [FILE]xxx.mp3|歌名.mp3
  → 后端下载（24 MB 上限）→ 落盘 → WS 推 agent_audio {url}
  → 对话界面 <audio controls>（支持 Range，可拖进度）
  → 桌宠气泡：「♪ 正在播放：歌名」
```

> ⚠️ 默认「文本模式」会等用户回序号，60 秒后回 `点歌超时！`。
> 说 **`点歌 歌名 1`**（带序号）才走单曲模式直接出文件。

### 3.3 语音（TTS）：**没有**

本仓库按裁决 **D1** 不引入 TTS 依赖，`voice` phase 只是预留态。
所以"她用语音念回复"不支持；**点歌 / 云端发来的音频能播**，这是两件事。

## 4. 消息模型（数据层核心）

### 4.1 消息身份与排序

```js
{
  id,          // 唯一身份：h-<dbid> / reply-<requestId> / local-<requestId> / attach-<ts>
  role, text, attachments[],
  ts,          // 排序键（毫秒），所有写入都必须带
  timeLabel, sourceLabel, requestId, streaming, optimistic
}
```

**两条铁律**（都由测试守住）：

1. **所有写入必须走 `setMessages()`** —— 写完立即按 `ts` 排序。
   禁止直接 `messages.value = [...]`（除 `setMessages` 内部与 `reset()`）。
2. **消息身份只能是 `id`，绝不能用 `role+text`**。
   实测一个会话里「发个表情包」出现了 **22 次**；用文本做身份会让重复对话被互相吃掉。

### 4.2 三条写入路径

| 路径 | 何时 | 作用 |
|---|---|---|
| `upsertReply(requestId, result)` | HTTP 返回 | 本轮权威结果；附件与已有附件**取并集**（不覆盖） |
| `attachToCurrentReply(item)` | WS `agent_image` 到达 | 挂到本轮消息；**全局 url 集合去重**（跨消息生效） |
| `appendHistoryRows(rows)` | `loadHistory` | 按 `id` 补缺；同一轮已上屏则跳过 |

### 4.3 排序兜底

`messageTs()` 取 `item.ts` → 否则从 id 里锚定解析 13 位毫秒 → 都不行则返回
**模块级常量 `FALLBACK_TS`**（恒定，排最后）。

> ⚠️ 这里踩过两次：① 用 `Date.now()+1000` 当兜底 → 每次比较都变，排序不稳定，消息乱跳；
> ② `const now` 定义在 `if` 块内却在块外 return → 直接 `ReferenceError`。

## 5. 气泡与徽标（渲染端）

### 5.1 说话气泡

| 项 | 值 | 说明 |
|---|---|---|
| 文字出现方式 | **整段直接铺满** | 曾用打字机 180ms/字 → 28ms/字，都嫌慢 |
| 停留时长 | **3 秒后自动消失** | 后端 `duration_ms=3000`；前端给兜底上限 |
| 图片模式 | **图文并存** | 图在上、文字在下；纯图才隐藏文字 |
| 身份色 | `data-agent-accent` + `!important` | 大肥鱼 `#2B6CB0` 鲸鱼蓝，DSH `#4F6BED` |

### 5.2 状态徽标

12 态各有专属底色（`.p-<phase>`）：待机灰 / 思考蓝 / 执行橙 / 完成绿 / 错误红 …

**身份色与状态色必须并存**：
- 左侧 3px 竖条 = **身份色**（区分谁在干活）
- 底色 = **状态色**（一眼看出在思考还是完成）

> ⚠️ 曾经写成 `background: <身份色> !important`，把 12 态底色全盖掉，
> 表现就是"徽标能显示工作状态，但颜色永远不变"。

## 6. 记忆（跨会话 / 跨设备）

### 6.1 存在哪

```
/opt/astrbot/data/plugin_data/astrbot_plugin_livingmemory/livingmemory.db
```

桌宠与微信**读写同一个文件**，区别在作用域字段 `session_id`。

### 6.2 作用域

| 模式 | 行为 | 采用 |
|---|---|---|
| `legacy` / `session` | 每会话独立 → 两边记忆互相看不见 | ✗（原值） |
| **`user`** | 同一用户跨会话共享长期记忆 | ✅ **当前** |
| `global` | 所有人共享 | ✗ 会污染 |

已执行迁移：`1070 条 → livingmemory:user:webchat:xiao1`（有备份）。

### 6.3 插件已有的能力（不用自己造）

- `recall_long_term_memory` —— 她可主动检索
- `memory_reflection` —— 每 20 轮自动摘要
- `graph_memory` —— 知识图谱（人物/偏好/事件）

### 6.4 为什么不能放云端网盘（AList）

`livingmemory.db` 是 SQLite **WAL 模式**（有 `-wal` / `-shm`，需要文件锁与共享内存），
`livingmemory.index` 是 FAISS 索引（mmap 随机读写）。
AList 是 HTTP 文件服务，两者都不支持 —— **技术上不可行，且没必要**（本来就在同一台机器上）。

AList 适合放**点歌的 mp3 缓存**（大文件、只读、支持 Range）。

## 7. 契约陷阱（改代码前必读）

1. **`/api/companion/chat-settings` 不存在** → 返回 404，前端静默回落默认值。
2. **`cloud_feiyu` 直通分支绕过 `chat_run_coordinator`** → `/chat/cancel` 对它无效，
   中断只能靠前端 `abort fetch`。
3. **历史接口的 `created_at` 是 ISO 8601**（`2026-10-22T23:30:12+08:00`），
   但 PowerShell 显示成美式格式，**别被终端输出骗了**。
4. **同一轮的 user 与 assistant 共享同一个 `request_id`** → 不能按它去重（会把提问全删）。
