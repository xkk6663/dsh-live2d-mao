# 大肥鱼多模态桥接 · 协议与修复记录

> 目标：桌面桌宠 ⇄ 云端 AstrBot（大肥鱼 persona）**双向**打通文本与附件（图片/语音/文件/视频），
> 从而"共用记忆和灵魂大脑、跨设备对话"。
> 记录时间：2026-10-22 · 验证环境：云端 AstrBot v4.29.1（http://127.0.0.1:6185）+ 本地后端 + 桌宠前端。

---

## 0. 一句话结论

**根因不是"解析错了图片 URL"，而是三处叠加：**

1. `[IMAGE]xxx.png` 是**云端附件目录里的文件名**，不是 URL；必须调 Open API 下载才能拿到字节。
2. **入站**（她发图 → 桌面）：旧代码把占位符当 URL 直接塞给前端 → `<img src="[IMAGE]xxx.png">` 必然裂图。
3. **出站**（桌面发图 → 她）：旧代码把 data URL 放进 `images=`，而 `_build_payload` 根本没把它写进请求体
   —— 桌面端发的图**从来没到过云端**（所以她"看不见"你发的图，而你以为发了）。

顺带修掉两个真实瑕疵：正文**重复两遍**、**英文思考混进正文**。

## 1. 出站：桌面 → 大肥鱼（图片必须先换 attachment_id）

AstrBot `POST /api/v1/chat` 的 `message` 字段收的是**消息段数组**，不是 data URL：

```json
{
  "username": "xiao1",
  "session_id": "d93c5ca6-…",
  "enable_streaming": true,
  "message": [
    {"type": "plain", "text": "这张图是什么颜色？"},
    {"type": "image", "attachment_id": "494be525-469c-4fc0-8396-67f7ac83c9aa"}
  ]
}
```

所以流程是两步：

1. `POST /api/v1/file`（multipart，字段名 `file`，需要 `file` scope）上传图片 → 返回 `attachment_id`；
2. 把 `{"type":"image","attachment_id":…}` 拼进 `message` 数组。

支持的段类型：`plain` / `image` / `record` / `file` / `video` / `reply`（`reply` 仅 chat 用）。

> 实现：`CloudFeiyuClient.upload_attachment()` + `_build_payload()` 拼段。
> 防呆：`_build_payload` 一旦发现 `images` 里还是 `data:` 开头，直接抛错而不是静默丢图。

## 2. 入站：大肥鱼 → 桌面（占位符 → 真实字节）

### 2.1 SSE 帧格式（实测）

```
data: {"type":"plain","data":"喏，给你看。\n\n","streaming":true,"message_id":"…"}
data: {"type":"image","data":"[IMAGE]20261022185913674_abe8.png","streaming":false,"message_id":"…"}
data: {"type":"attachment_saved","data":{"id":"946e7ab2-b426-4c0f-a21b-d87753004be6","type":"image"}}
data: {"type":"complete","data":"整段全文…","reasoning":"模型的思考过程…"}
data: {"type":"end","data":""}
```

占位符规律（源码 `astrbot/core/platform/sources/webchat/webchat_event.py`）：

| 类型 | data 形状 | 说明 |
|---|---|---|
| 图片 | `[IMAGE]<存储文件名>` | 文件落在云端 `data/attachments/` |
| 语音 | `[RECORD]<存储文件名>.wav` | |
| 文件 | `[FILE]<存储文件名>|<原始文件名>` | `|` 后是给用户看的名字 |
| 视频 | `[VIDEO]<存储文件名>` | |

### 2.2 下载接口（两种都能用）

| 接口 | scope | 说明 |
|---|---|---|
| `GET /api/v1/files/content?filename=<文件名>` | `file` | **推荐**，直接从占位符拿到字节 |
| `GET /api/v1/files/<attachment_id>/content` | `file` | 用 `attachment_saved` 帧里的 id 下载 |

两者都返回 `application/octet-stream`，实测 PNG 魔数 `89504E47`、WebP `RIFF` 正确。
平台**不需要**走 dashboard 登录态（`/get_attachment` 那条路才需要）。

### 2.3 实现要点

`CloudFeiyuClient.chat_stream_full()` 在 `attachment_saved` / 占位符 / `end` 三处触发下载，
把附件转成 `data:<mime>;base64,…` 再 yield；同时通过 `session_out["attachments"]` 给出结构化元信息。
下载失败不会中断回复（`FeiyuAttachment.error` 记录原因，前端显示"加载失败/取不到"）。

## 3. 三个"看起来像 bug 其实有原因"的坑

### 3.1 正文重复两遍

AstrBot **先逐 token 推 `plain`，最后再推一个 `complete` 帧，而 complete 的 data 是整段全文**。
两路都累加就会变成 `"XXX…XXX…"`。
**规则：出现过 `plain` 就只认 plain；只有全程没有 plain 时才用 `complete` 兜底。** 绝不能追加。

### 3.2 英文思考混进正文

`complete` 帧虽然带独立的 `reasoning` 字段，但直连自部署版本会在正文开头漏出英文思考，例如：

```
Could be a test of "你是谁，我在哪" — maybe they're drunk? No. Just answer.大肥鱼。你在自己电脑前…
```

关键难点：思考与中文正文**粘在同一行**。上层 `companion.py` 原来只做"第一行不含中文就丢"，
对这种形状完全无效。现在在 client 层做行级清洗 `strip_reasoning_prefix()`：

- 整行没有中日韩字符且像句子 → 丢弃；
- 英文句子后面**粘连**中文 → 只保留中文起头那段；
- 英文句子里**引用**了中文原话（`of "你是谁，我在哪"`）→ 跳过引号内中文，找回引号闭合后的正文；
- 有序列表（`1. 第一点`）与正常中文、中英混排**不误伤**（有单测钉住）。

### 3.3 `⟦MODE:chat⟧` / `&&happy&&` 在桌宠气泡里闪现

流式期间每个 chunk 都被 `agent_stream` 推给气泡，而上层清洗只在**流结束后**做一次
→ 用户会看到内部标记一闪而过。现在在 client 的取文本环节就剥掉
（`strip_control_markers()`），流到哪里都是干净文本。

另外：流式期间已推出去的英文思考无法撤回，所以收尾时若清洗结果与原文不同，
后端会再发一条带 `replace: true` 的 `agent_stream`，让前端**整体替换**气泡内容。

## 7. 桌宠气泡：为什么她的话"显示不出来"（2026-10-22 二次修复）

用户反馈「大肥鱼的对话气泡显示不出来文字和图片」，并且「气泡要鲸鱼娘专属蓝色方便区分」。查下来是**四个独立原因叠在一起**：

| # | 原因 | 后果 | 修法 |
|---|---|---|---|
| 1 | 后端只发 `agent_stream`，而渲染端把它定向到**横条 #pet-strip**（用户 10-17 裁决：流式正文走横条） | 气泡永远收不到正文 | 补发 `agent_bubble`（气泡专用通路），横条那条保持不变 |
| 2 | `agent_image` 走 `showImageInBubble()`，那是"点击互动随机图"的入口：固定 **3 秒**自毁、且沿用点击互动的身份色 | 表情包三秒就没了 | 带 `agent_id` 的图片改走"Agent 图片"分支：身份色 + `hold_ms` 停留 |
| 3 | `hideSpeechBubble()` **不清 `img.src`** | 显示过图之后，下次来文字时 `image-mode` 一加上，文字气泡突然变成**上一张旧图** | 隐藏时清 `src` + `hidden=true` |
| 4 | DSH 每 2 秒播报「正在用 pwsh 干活…」（`dsh_signals.py:80`），会**顶掉**她正在说的话 | 气泡里只剩工具播报，看起来"她没说话" | 跨身份抢占保护：当前气泡正在打字/停留时不接受别的身份插话（同身份仍可打断） |

**配色**（用户要求"专属蓝、方便区分"）：

- 大肥鱼身份色 = `#2B6CB0`（鲸鱼蓝），在 `companion.py` 的 `FEIYU_BUBBLE_ACCENT`，同时经 `agent_bus_service.register()` 注册进总线
  （徽标与 `/api/companion/agents` 快照都靠它；DSH 当年就是漏了注册导致气泡不变蓝，见 `dsh_adapter.py:972` 注释）。
- 气泡调色板由 `accent 7% + 白` 提到 **底 16% / 边 82% / 字 66% 压深 / 外发光 24%** —— 7% 在白桌面上根本看不出蓝。
- **身份色必须优先于皮肤**：皮肤系统把调色板写成内联变量，内联优先级最高，用户选了「磨砂玻璃/霓虹/墨黑」就会把身份蓝整个盖掉。
  已按 `docs/DSH桌宠深度融合技术方案.md:223`「插件身份色优先于皮肤——气泡颜色跟"谁在说话"走」加 `!important` 覆写，
  皮肤保留质感（模糊/渐变/描边）、身份色负责色相；深色皮肤另给浅色文字分支。
- 徽标整枚改用身份色（此前只有左边一条竖线是身份色，底色还是按工作阶段的橙/绿/青）。
- 气泡位置会**避让 Agent 徽标**（矩形相交时上移/下移），不再盖住 chip。

> 渲染端改动文件是 `dist/live2d-pet/live2d-pet.js` 与 `live2d-pet.css`（dist 即源码层，按 AGENTS.md §3.1 升了 `?v=`）。

## 9. 图片 / 音频 / 点歌（2026-10-22 第三个需求）

需求原话：「图片、语音、发送 mp3 音频的点歌功能不能少」。

### 9.1 点歌：根本不该自己造，云端已有插件

调研发现云端 AstrBot 装了 **`astrbot_plugin_music`**（播放器 `nj点歌` → `nodejs_base_url=172.18.0.1:3000`，
实测 Node 音乐 API 正常、能拿到 `mp3` 的 `audio_url`）。所以**桌宠端不实现音乐搜索**，只负责：

1. 用户在桌宠里说「点歌 晴天 1」→ 照常走 `/api/companion/chat`；
2. 云端的点歌插件把歌作为 **`[FILE]xxx.mp3|晴天(深情版)_Lucky小爱.mp3`** 帧发回；
3. 后端下载 → **落盘** → WS 推 `agent_audio{url}` → 桌宠播放。

> ⚠️ **单曲模式**：默认 `select_modes` 含 `text(文本模式)`，它会**等用户回一个序号**，
> Open API 没有人回话，结果 60 秒后 `点歌超时！`（实测）。说「点歌 <歌名> 1」即可走单曲模式直接出文件。

### 9.2 一个必须记住的硬限制：**WebSocket 单帧 1MB**

这是本次最贵的一课。最初把附件字节内联进 `agent_image` / `agent_audio` 的 `data:` URL，结果：

```
sent 1009 (message too big) frame with 11145877 bytes exceeds limit of 1048576 bytes
```

整条 WS 被踢掉，**连聊天一起断**。触发它的是两个来源：

| 来源 | 原始大小 | base64 后 |
|---|---|---|
| 一首歌 mp3 | 11.1 MB | ≈ 15 MB |
| 云端表情包（png） | **3.6 MB** | **14.2 MB** |

**规则：任何体积不可控的二进制都不得进 WS。** 现在图片和音频一律：

```
下载 → 落盘 <pet状态>/agent_media/<sha256前16位>.<ext> → WS 只推
/api/companion/agent-media/<name> → 渲染端 <img>/<audio> 走 HTTP
```

好处不止是不断线：`<audio>` 拿到的是**支持 Range 的 HTTP URL**（实测 `206 Partial Content`），
可以拖动进度；落盘按内容哈希命名，重复点同一首歌不会重复占空间，只保留最近 24 个。

### 9.3 顺手修掉的三个真 bug

| bug | 现象 | 根因 |
|---|---|---|
| 歌曲被当成图片 | 前端收到 `agent_image`，url 却是 `data:audio/mpeg` | `chat_stream_full` 的第二个返回值把**所有**附件都给了（调用方当 `<img>` 用），现已只返回 image |
| 点歌被判"附件过大" | 10.6MB 的歌直接失败 | 下载上限 8MB 是为图片定的；现在图片 8MB、其它 24MB |
| 上传接口不存在 | "桌面发的图她看不见" | `_build_payload` 从未把 `images` 写进请求体（上一轮已修，这里记录） |

### 9.4 语音：现状要说清楚

**本仓库没有 TTS**（裁决 D1：不引入 TTS 依赖）。桌宠渲染端的语音播放代码仍在调用
`/api/companion/voice/stream`，**而后端没有这个路由** —— 那条链路是断的，不是本次引入的问题。

本次新增的 `agent_audio` 通路**不依赖 TTS**：播放的是云端已经合成/下载好的音频文件
（点歌的 mp3、云端语音消息的 `[RECORD]`）。所以：

- ✅ **点歌 / 云端发来的语音 → 能播**
- ❌ **"让大肥鱼用语音念她的回复" → 仍然不支持**（需要单独做 TTS，属新决策）

## 10. 跨会话 / 跨设备记忆（2026-10-22 核心需求）

### 10.1 用户的判断是对的：**不能硬统一上下文**

一开始的诉求是"两边共用同一个上下文"，但硬合并会让微信和桌宠互相串味（微信有群聊、不同场景）。
正确的分层是：**上下文各自独立，只共享"长期记忆层"**。

### 10.2 现状测绘（实测 AstrBot + livingmemory）

| 层 | 存储 | 现状 |
|---|---|---|
| 上下文链 | `data_v4.db` → `conversations` | 微信（`weixin_personal_mgwh`）与桌宠（`webchat`）**各自一条**，这是对的 |
| 记忆条目 | `livingmemory.db` → `graph_entries` / `memory_atoms` / `documents` | 929 / 113 / 28 条，**按 `session_id` 分桶** |
| 检索 | `graph_vector_retriever.search()` | `session_id` 非空就**强制按它过滤** → 两边记忆互相看不见 |
| 主动检索 | `recall_long_term_memory` 工具 | **已开启**，她可以主动问"我之前和用户聊过什么" |
| 自动摘要 | `memory_reflection`（`summary_trigger_rounds=20`） | **已开启**，每 20 轮自动提炼 |
| 知识图谱 | `graph_memory.enabled=true` | 247 节点 / 787 边，人物·偏好·事件成网 |
| 定期整合 | `memory_consolidation.enabled` | 原本 **false** |

**结论**：用户设想的「两边自动摘要 → 存进共享仓库 → 她主动检索」，**插件已经全都有**，
缺的只是让"摘要仓库"跨会话可见 —— 也就是作用域。

### 10.3 落地：`memory_scope_mode` = `user`（不是 global）

`core/memory_scope.py:128 resolve_memory_scope()` 的四种模式：

| 模式 | 行为 | 是否采用 |
|---|---|---|
| `legacy`（原值） | `use_session_filtering=true` → 每会话独立 | ✗ 就是"记不住微信"的原因 |
| `session` | 每会话独立 | ✗ |
| **`user`** | `livingmemory:user:<平台>:<身份>`，同一用户跨私聊/群聊共享 | ✓ **采用** |
| `global` | `livingmemory:global`，所有人共享 | ✗ 会污染，不采用 |

> ⚠️ 注意 `user` 作用域里带 `平台` 前缀，微信和桌宠是**不同平台**，
> 所以本次迁移把两边显式写进同一个 `webchat` 作用域：
> `livingmemory:user:webchat:xiao1`。

**执行记录**（已在云端完成，有备份）：

```
plan: 1070 entries -> livingmemory:user:webchat:xiao1
[作用域迁移] 已迁移 documents=28 atoms=113 graph_entries=929
remaining: 0
备份: livingmemory_before_scope_1792673965.db
```

**验证**：在桌宠端问「你还记得我微信里跟你说过什么吗」，她答出
「凌晨一点多你还问我睡了没」「说广州三十度你嫌冷」—— 这些全在微信侧的记忆里。

> ⚠️ 迁移命令 `/lmem migrate-scope` 走消息管道，需要管理员身份（`admins_id=["astrbot"]`），
> 通过 Open API 注入无反应且无日志。本次改为直接调用插件的 `ScopeMigrator`
> （`survey()` → `plan()` → `execute(backup_path=...)`），与命令走同一条实现。

### 10.4 还能再优化什么（下一步）

1. **开启 `memory_consolidation`**（`enabled=false` → `true`, `granularity=session`）：
   定期把零散记忆聚合成更精炼的条目，控制规模。记忆变成 1000+ 条后有价值。
2. **`recall_engine.top_k` 从 3 提到 5~8**：现在只召回 3 条，跨会话信息变多后容易漏。
3. **`enable_agentic_recall_beta = true`**：允许她**多轮**主动检索（现在最多 1 轮），
   对"你还记得我之前说的那个吗"这类模糊提问更稳。
4. 明确**不要**用 `global`：多用户/多群会互相污染。
