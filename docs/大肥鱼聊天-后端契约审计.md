## 1. `POST /api/companion/chat` 契约

### 1.1 请求体（`CompanionChatRequest`）

`routes/companion.py:280-285`：

```python
class CompanionChatRequest(BaseModel):
    message: str = Field(default="", max_length=4000)
    model_id: str = Field(default="auto", max_length=200)
    reasoning_level: str = Field(default="auto", max_length=50)
    images: list[CompanionChatImageRequest] = Field(default_factory=list, max_length=5)
    client_request_id: str = Field(default="", max_length=80, pattern=r"^[A-Za-z0-9._:-]*$")
```

`CompanionChatImageRequest`（`:275-277`）：`{ name: str (默认 "粘贴的图片.png", ≤120 字), data_url: str }`。

**硬约束**（前端必须在本地先挡，否则是 422 而不是友好报错）：

| 字段 | 约束 | 证据 |
|---|---|---|
| `message` | ≤ 4000 字（**超长 422**），可为空（但只要 `images` 非空就算合法） | `:281`、`:1401-1408` |
| `images` | **最多 5 张**（`max_length=5`） | `:284` |
| `client_request_id` | ≤ 80 字，**只允许 `[A-Za-z0-9._:-]`**；UUID（含 `-`）合法 | `:285` |
| `data_url` | 必须 `data:image/<...>;base64,<...>` | `image_service.py:162-165` |

### 1.2 `model_id` 取值语义（**这是最关键的一条**）

`routes/companion.py:1417-1462` 的判定顺序：

```
requested_model = payload.model_id.strip()
if not requested_model or requested_model == "auto":
    requested_model = config.get("pet_chat_model_id") or "auto"      # :1436-1437
if requested_model == "auto":
    route = select_auto_route(...)                                   # :1441-1448  ← 本地自动路由
else:
    if requested_model == "cloud_feiyu": selected_model = "cloud_feiyu"   # :1451-1452
    else:                                selected_model = resolve_model_id(requested_model)  # :1454
```

| 前端传 | 实际行为 | 是否"保持原有功能" |
|---|---|---|
| `"cloud_feiyu"` | **直通 AstrBot 人格 333**，跳过全部本地 LLM / 路由 / agent 工具 | ✅ **唯一正确值** |
| `"auto"` 或 `""` | 读 `config.pet_chat_model_id`（本机未设置 → 仍是 `"auto"`）→ `select_auto_route` → **本地大模型** | ❌ 人格/记忆全变 |
| 其它真实模型 id | `resolve_model_id()` → `get_model_profile(id).id`（`llm.py:304-308`），未知 id 抛 `LLMConfigError` → HTTP 400 | ❌ 同上 |

> ⚠️ `pet_chat_model_id` / `pet_chat_reasoning_level` **两个键根本不在默认配置里**（`companion/companion_service.py:66+` 的 `DEFAULT_CONFIG` 无此键；`configuration.py:229-248` 的白名单也不含），
> 本机 `数据/桌宠/设置.json` 里也确实没有。也就是说：**前端只要传 `auto`，今天一定走本地模型**，大肥鱼人格立刻消失。

`cloud_feiyu` 本身在注册表里是一个"虚拟模型"：`model_registry.py:634-657`（`display_name="大肥鱼（云端）"`、`provider_id="astrbot"`、`supports_vision=False`、**价格全 0**）。
它**不走** `resolve_model_id` 而是被硬编码短路（`:1451-1452`），所以不受注册表影响；但 `:1467-1473` 会检查 `feiyu.is_configured`，未配 `ASTRBOT_API_KEY` 时抛 502。

### 1.3 `reasoning_level` 可用值

- 普通（非 `cloud_feiyu`）分支：最终由 `normalize_model_reasoning()` 收敛到该模型的 `options`（`model_registry.py:117-159`）：
  DeepSeek 系列 = `off|low|high|max`；gpt-5/o1/o3/o4 = `low|medium|high`；其余 = `default`。另有旧值映射 `fast→low / standard→medium / deep→high`（`:155`）。
- **`cloud_feiyu` 分支：该字段被强制覆盖为 `"off"`**（`routes/companion.py:1466`），传什么都不影响。响应里也回 `reasoning_level: "off"`（`:1541`）。
- 结论：**前端在 `model_id=cloud_feiyu` 时可以把"思考档位"控件隐藏或置灰**；传 `auto` 即可。

### 1.4 `client_request_id` 幂等语义（`claim_request`）

指纹字段（`routes/companion.py:1363-1378` → `request_fingerprint()` 对 dict 做 `json.dumps(sort_keys=True)` 再 SHA-256，`chat_idempotency.py:21-23`）：

```python
{"channel": "companion_chat", "conversation_id": "desktop_pet",
 "message": message, "model_id": payload.model_id, "reasoning_level": payload.reasoning_level,
 "images": [{"name": item.name, "content_hash": sha256(item.data_url)} for item in payload.images]}
```

判定逻辑（`:1381-1386` + `messages_repository.py:122-160`）：

| 情况 | 结果 |
|---|---|
| 首次出现（或 `client_request_id` 为空 → 自动生成 uuid） | 正常处理 |
| 同 id + **同指纹** + `status == succeeded` | **直接回放缓存响应**（不再调模型，HTTP 200）`:1382-1383` |
| 同 id + 同指纹 + `status == pending` | **HTTP 409** `{code:"chat_request_in_progress"}` `:1386` |
| 同 id + 同指纹 + `status == failed` | 按原 `http_status` 重抛 `:1384-1385` |
| 同 id + **指纹不同** | `ValueError("同一个对话请求ID不能用于不同内容。")` → **HTTP 400** `:1379-1380`、`messages_repository.py:158-159` |

**前端重试的正确姿势**：真正网络失败（`network_error`）时，**沿用同一个 `client_request_id` 重发**——要么命中缓存回放，要么 409（此时说明后端还在跑，应等待而不是换 id）。
**绝对不能**在"用户改了一个字/加了一张图"后复用旧 id（指纹变了 → 400）。现有 `useCompanionChat.js:175` 每次发送生成新 uuid 是对的。

### 1.6 `POST /api/companion/chat/cancel`

`routes/companion.py:1694-1705`：

```python
cancelled = await chat_run_coordinator.cancel(DESKTOP_PET_CONVERSATION_ID, source="desktop_pet",
                                               reason=f"user_cancelled:{payload.client_request_id or 'unknown'}")
return {"cancelled": cancelled, "conversation_id": "desktop_pet", "client_request_id": payload.client_request_id}
```

- **取消粒度 = "该会话（`desktop_pet`）+ 该 source（`desktop_pet`）的当前 active run + 队列"**（`conversation_runtime.py:181-217`）。
- **`client_request_id` 只被写进取消原因字符串，不参与匹配**（`:1697-1699`）→ 传空串也能取消。
- **对 `cloud_feiyu` 分支无效**：该分支在 `:1465` 就直接 `async for chunk in feiyu.chat_stream_full(...)`，**从未进入 `chat_run_coordinator.submit()`**（对比本地分支 `:1555` → `chat_with_ai` → `chat_service.py:1263`）。所以 `cancelled` 会是 `0`。
- 取消成功的那个请求会抛 `ChatRunCancelledError` → HTTP **409** `{code:"request_cancelled"}`（`:1578-1585`）。
- **前端能做的取消 = `AbortController.abort()`**：断开 HTTP 后，后端协程在下一次 `yield` 处被取消，已产生的 chunk 不会落库（`cloud_feiyu` 分支本来就不落库，见 §5）。

### 1.7 `cloud_feiyu` 分支的文本后处理（流式上屏必须与之对齐）

`:1511-1533`：

1. `feiyu_content = "".join(collected)`（等全部流完才拼）
2. 取第一个 `&&(\w+)&&` 作为 `speech_emotion`，然后**从全文删除所有 `&&\w+&&`**（`:1514-1517`）
3. 删除 `⟦...⟧` 形式的 `MODE` 标记（`:1519`）
4. **逐行删掉开头所有"不含中文字符"的行**（`:1521-1533`）——用于剥掉模型开头输出的英文思考/指令

> ⚠️ 因此 **`payload.text` 逐块拼起来的字符串 ≠ 最终 `reply`**。前端若"流式铺 + 最终替换"，在收尾时必须**用 `result.reply` 覆盖**，否则会把 `&&happy&&`、英文思考行留在屏幕上。
> 更保守的做法（推荐给第一版）：**流式只用于"进度条/打字光标"提示，正文以 `result.reply` 一次性落定**。

## 2. 图片链路

### 2.1 是否真正被后端消费？——**是**（两条分支都消费，但方式完全不同）

| 分支 | 图片去哪了 | 证据 |
|---|---|---|
| `cloud_feiyu` | 转成 `list[str]` 的 data URL 列表 → `feiyu.chat_stream_full(images=...)` | `:1479-1493` |
| 本地模型 | `image_attachments=images` → `chat_with_ai` → `_build_user_content()` 拼成 OpenAI 多模态 `content` 数组 | `:1555-1568`、`chat_service.py:961-980` |

**但两条分支对"识图"的判定不同**：

- **`cloud_feiyu`：不看 `supports_vision`，无条件传**。虽然 `model_registry.py:643` 把 `cloud_feiyu` 标成 `supports_vision=False`，但直通分支根本不经过 `resolve_model_id`/`model_supports_vision`，所以这个标记**对本次链路无效**。
- **本地分支**：`send_images_to_model = bool(images and image_input_enabled and model_supports_vision(selected_model))`（`chat_service.py:1421-1422`）。选到不支持识图的模型时，**图片会被静默丢弃**（只在历史里留 `[图片 N 张]` 占位，`:955-958`）。

> ⚠️ **风险点（不阻塞）**：`cloud_feiyu/client.py:95` 有一行注释 `# 图片暂不支持多模态格式，后续再加`，而 `_build_payload()` **确实没有把 `images` 写进请求体**（`:83-96` 只放了 `message/session_id/username/platform_id/enable_streaming`）。
> 即 **后端承诺会传，但底层客户端当前把 images 参数吞掉了**。真机行为取决于 AstrBot 是否解析 `message` 里的图片——目前**图片大概率不会真的让大肥鱼"看到"**。
> 前端侧建议：**UI 上允许选图并上屏展示（本地预览），但不要对"它能看见图"做强承诺**；同时把这个差异报给后端负责人（本任务只读，不改）。

### 2.2 `image_attachment_from_data_url` 的格式要求与上限

`image_service.py:162-180`：

| 要求 | 细节 | 证据 |
|---|---|---|
| data URL 前缀 | 必须 `data:image/...` 且**含 `;base64`**，且必须带 `,` 分隔 | `:163-165` |
| base64 | `base64.b64decode(encoded, validate=True)` —— **严格校验**，含换行/空格会失败 | `:166-169` |
| 大小上限 | `settings.qq_image_max_bytes`，**默认 8 MiB**（`QQ_IMAGE_MAX_BYTES`，范围 1 MiB–50 MiB） | `:170-171`、`config.py:306`、`:141-142` |
| MIME 白名单 | `image/jpeg|png|gif|webp` | `image_service.py:16`、`:172-174` |
| 不合法 MIME 的兜底 | 尝试 `_normalise_raster_image()` 重新编码成 png/jpeg（**仅限 Pillow 能打开的位图**） | `:174`、`:71-86` |
| 尺寸上限（仅兜底路径） | 像素积 > 5000 万 → `RuntimeError`；超 4096 长边会缩 | `:75-77` |
| 校验失败 | HTTP **400**，`detail.code = "invalid_chat_image"`，**同时把该 `client_request_id` 标记为 failed** | `routes/companion.py:1388-1400` |

> 注意第 400 条的副作用：**因为图片格式错误而失败的 id 已被判 failed**，之后再拿这个 id 重试会直接重抛 400（`claim.status == failed`，`:1384-1385`）。改图重试**必须换新 `client_request_id`**。

图片数量：请求体层 `max_length=5`（`:284`）；`image_service.py:217` 里另有 `qq_image_max_count`（默认 3）限制——**但 `image_attachment_from_data_url` 不经过 `load_image_attachments`**，所以 3 张的限制**不生效**，实际上限是 **5**。

## 3. 流式：WS 通道、事件形状、可行性

### 3.1 端点

`routes/companion.py:154-156`：

```python
@router.websocket("/ws")
async def companion_websocket(websocket: WebSocket):
    await pet_event_service.serve(websocket)
```

→ URL = **`ws(s)://<当前 host>/api/companion/ws`**（router prefix `/api/companion`，`companion.py:47`）。
桌宠渲染端就是这么连的：`澪Agent应用/dist/live2d-pet/live2d-pet.js:3151-3152`。

### 3.2 信封与事件形状

发送（`companion/pet_event_service.py:194-198`）：

```json
{ "type": "<event_type>", "timestamp": "2026-10-22T17:00:00+08:00", "payload": { ... } }
```

`cloud_feiyu` 发布的两种事件（`routes/companion.py:1494-1509`）：

```json
{ "type": "agent_stream", "timestamp": "...",
  "payload": { "text": "<增量 chunk>", "agent_id": "cloud_feiyu", "accent": "#4a9eff" } }

{ "type": "agent_image", "timestamp": "...",
  "payload": { "url": "<图片 URL>", "agent_id": "cloud_feiyu" } }
```

> ⚠️ **这不是 `agent_bus_service.stream()` 的标准形状**。标准 `agent_stream` 带 `texts[]` / `dt[]` / `final_text` / `frame:"text-chunks"`（`kernel/agent_bus_service.py:393-431`），
> 而 `cloud_feiyu` 走的是裸 `pet_event_service.publish()`，只有 `text` 字段。
> 直接后果：桌宠渲染端的 `applyAgentStream()` 会因为 `frame !== 'text-chunks'` 或 `texts` 为空而 **`.ts:3515-3521` 直接 return** → **桌宠横条不会显示大肥鱼的流式正文**（这是既有的、与本次改造无关的现状）。
> 对**聊天页自己**而言反而是好事：字段简单（就是 `payload.text`），不需要处理 `texts/dt`。

其它会出现在同一 socket 上的事件（避免前端误吞）：`ready`（`:229-238`，带 `protocol_version: 3` / `settings` / `activity` / `screen`）、`pong`、`speak`（`pet_event_service.py:405-421`，来自 2 s 轮询落库 assistant 消息）、`foreground_changed`、`agent_status`、`agents_snapshot`、`activity`、`settings_changed`。

客户端 → 服务端可发：`{"type":"ping","payload":{}}`（`:248-249`），服务端回 `pong`。

### 3.3 可行性结论：**可行，但有 4 个必须先决条件**

| 结论 | 说明 | 证据 |
|---|---|---|
| ✅ **能只订阅 `agent_id == "cloud_feiyu"`** | 事件里显式带了 `agent_id`，前端可据此过滤 | `:1499` |
| ✅ **`text` 是增量 chunk** | `async for chunk, imgs in feiyu.chat_stream_full(...)` 直接 publish 未拼接的 `chunk` | `:1489-1501`、`cloud_feiyu/client.py:166-195` |
| ✅ WS 握手后会先收到 `ready` | 可用它作为"连接就绪"标志 | `pet_event_service.py:229-238` |
| ⚠️ **`publish` 在无客户端时静默丢弃** | `publish()` 里 `if loop is None or not has_clients: return` —— 前端没连 WS 时流式**完全没有**，不影响最终 `reply` | `pet_event_service.py:216-222` |
| ⚠️ **没有"这一轮开始/结束"的事件** | 没有任何 `agent_stream_start` / `done`。前端只能靠"自己 POST 之后收到的第一个 chunk"推理开始，靠 **HTTP 响应回来**推理结束 | `:1489-1553`（无配对事件） |
| ⚠️ **广播不分客户端来源** | `publish` → `broadcast` 给**所有** WS 客户端（含桌宠渲染端） | `pet_event_service.py:206-222` |
| ❌ **`cloud_feiyu` 的流不进协调器** | 不能靠 `/chat/cancel` 停；也不会被后续消息"替换" | `:1465-1553` vs `conversation_runtime.py:130-179` |

**推荐的前端流式时序（最稳）**：

```
1. 打开 WS（或复用单例），等 ready
2. POST /api/companion/chat（fetch，不 abort）
3. onmessage: type==='agent_stream' && payload.agent_id==='cloud_feiyu' → 累加 payload.text（或按需渲染）
4. POST resolve → **丢弃累加结果，用 result.reply 落定**（因为后处理会改写文本，见 §1.7）
5. 用 result.speech_emotion / model_id / tool_receipts 更新 UI 元信息
```

**"这个 chunk 是不是我这一轮的"如何判定**：后端 **没有**在 `agent_stream` payload 里带 `client_request_id`（`:1497-1501` 只有 `text/agent_id/accent`）。
所以前端只能靠"同一时刻会话（`desktop_pet`）只可能有一轮在跑"这个**弱不变量**——而它**并不成立**：微信/QQ/主动消息也会往同一个 `desktop_pet` 会话写，并且 `/api/companion/chat` 之间没有互斥（见 §5.3）。**必须在 UI 上接受"偶发串台"**，或只在"自己发送中"才接受流式。

## 5. 历史消息持久化与"乐观消息 + 轮询对齐"

### 5.1 `_desktop_pet_conversation_id()` 是**单一固定会话**

```python
DESKTOP_PET_CONVERSATION_ID = "desktop_pet"          # routes/companion.py:48
def _desktop_pet_conversation_id() -> str:
    return DESKTOP_PET_CONVERSATION_ID                # :399-400
```

- `GET /api/companion/chat/history?limit=1..500（默认 120）` 只读这一个会话（`:2048-2051`）。
- 返回 `{conversation_id: "desktop_pet", messages: [{id, role, content, source, created_at, request_id, model_id, provider_model, reasoning_level}]}`（`:2052-2068`）。
- **没有**：多会话、分页、`before_id`、游标、图片、`emotion`。
  - 注：`attachments_json`/`emotion` 在 DB 里**有**（`conversation_repository.py:25-41` 的 `get_recent_messages` 选了它们），但 history 端点**没有映射出来**（`:2054-2066`）。**历史里拿不到图片** → `useCompanionChat.js:60` 的注释是对的。
- **增量对齐**有另一条路：`GET /api/companion/feed?after_id=N`（`:2084-2113`）——只回 `role='assistant'` 且带 `emotion`，是给桌宠"念新回复"用的，**不适合当聊天历史**。

> **结论**：**只能做单会话**。UI 上的"会话抽屉/多会话"必须关掉（`FeiyuChatPage.vue:79` 的 `showDrawer` 默认 `false` 正是为此）。

### 5.2 落库时机：**`cloud_feiyu` 分支完全不落库！**

| 分支 | user 消息落库 | assistant 消息落库 | 证据 |
|---|---|---|---|
| 本地模型 | `chat_service.py:1429-1439`（调模型**之前**） | `:1699-1722`（拿到回复后） | — |
| **`cloud_feiyu`** | **无 `db.save_message` 调用** | **无** | `routes/companion.py:1464-1553` 全段 |
| 兜底/确定性回复 | `:1380-1399`（仅本地分支的 local_reply 路径） | 同 | — |

**所以：用 `model_id=cloud_feiyu` 聊天，刷新页面后历史里一条都不会有。** 这解释了为什么老聊天页"看起来能用但翻不到记录"。

`chat_requests` 表**会**记录这一轮（`claim_request` 插入 pending `:1363-1378` → `complete_chat_request` 置 succeeded `:1681`），但它**不是** `messages` 表，`/chat/history` 读的是 `messages`。

`complete_chat_request` 必须在 `status='pending'` 时才成功（`messages_repository.py:176-177` 否则抛 `RuntimeError`）→ 若同一 id 被并发两次，第二个会 500。前端不要并发同 id。

### 5.3 乐观消息 + 轮询对齐的注意事项

1. **不要**依赖 `request_id` 去 `/chat/history` 里找本轮——`cloud_feiyu` 根本不落库。
2. 现有 `useCompanionChat.js:152-159` 的 8 s 轮询在 `cloud_feiyu` 下**永远拿不到自己刚发的消息**，会把乐观消息一直留着；一旦别人（微信/QQ）往 `desktop_pet` 写了新消息，轮询会**突然插进一条无关消息**——这是**预期行为**（单会话共享），UI 上最好用 `sourceLabel` 标明来源（`useCompanionChat.js:22-32` 已做）。
3. `appendHistoryRows()` 的去重键是 `role + '\0' + text`（`:114-117`）。`cloud_feiyu` 的历史为空 → 去重永远不触发；若以后后端补上落库，**同文重复**（用户连发两条一样的话）会被误去重。建议**改用后端 `id` 做主键**。
4. **乐观消息的清理**：发送失败时 `useCompanionChat.js:225` 只保留 `assistant` 乐观行，这是合理的；但对 `cloud_feiyu` 更简单——**失败就整行回滚 + 提示**，因为服务端没落库。
5. **并发**：`/chat` 的 `cloud_feiyu` 分支**绕过了 `chat_run_coordinator`**（§1.6），所以**同一会话可以同时跑 N 轮**（本地分支不会：`chat_service.py:1315` 的 `_conversation_lock`）。前端必须自己串行化（`sending` 标志已在 `useCompanionChat.js:171` 做了）。

## 7. 给前端的具体接线建议

```js
// 澪Agent应用/src/services/companionChatApi.js —— 扩展（保持现有导出不变）
export const FEIYU_CLOUD_MODEL_ID = 'cloud_feiyu'                    // 永远传它，别传 'auto'

 *  @returns {Promise<FeiyuChatResponse>}  // {reply, replies, speech_emotion, request_id, client_request_id,
 *                                       //  model_id, provider_id, provider_name, provider_model,

export const sendCompanionChat = (p, signal) => apiRequest('/api/companion/chat', {
  method: 'POST', deadlineClass: 'model',                             // 240 s；cloud 分支可能慢
  body: JSON.stringify({
    message: p.message || '',
    images: (p.images || []).slice(0, 5),                             // 后端硬上限 5

    client_request_id: p.client_request_id,                           // 新 uuid；网络重试沿用同一 id
  }), signal,
})

/** 打开/复用单例 WS：ws(s)://<host>/api/companion/ws
 *  @param {(ev:{type:string,payload:object})=>void} onEvent
 *  @returns {{close:()=>void}}   // ready / agent_stream(agent_id==='cloud_feiyu', payload.text 增量) / agent_image
 */
export function connectCompanionSocket(onEvent) { /* … */ }

/** 历史：单会话、最多 500 条、无分页、无图片 */
export const loadCompanionChatHistory = (limit = 200) =>
  apiRequest(`/api/companion/chat/history?limit=${encodeURIComponent(limit)}`,
             { deadlineClass: 'read' })   // → { conversation_id:'desktop_pet', messages:[…] }

/** 取消：对 cloud_feiyu 只 abort fetch 才有效；/chat/cancel 对它是 no-op */
export const cancelCompanionChat = (clientRequestId) =>
  apiRequest('/api/companion/chat/cancel', { method: 'POST', deadlineClass: 'mutation',
             body: JSON.stringify({ client_request_id: clientRequestId || '' }) })
```

**落地要点（按优先级）**

1. `model_id` **永远写死 `cloud_feiyu`**；下拉里只放 `大肥鱼（云端）`（或改成只读徽标）。
2. 发送用 `AbortController`；**停止按钮 = `abort()`**，再顺手 POST `/chat/cancel`（无害）。
3. 流式：自建 WS 单例，只在 `type==='agent_stream' && payload.agent_id==='cloud_feiyu'` 时累加 `payload.text` 做"打字机预览"，**HTTP 响应回来后一律用 `result.reply` 覆盖**（剥离 `&&表情&&` 等由后端完成）。
4. 历史：单会话、不做会话抽屉；**不要指望刷新后能看见刚才的对话**（`cloud_feiyu` 不落库），刷新后历史为空的兜底 UI 要写。
5. 图片：本地预览 + 最多 5 张；`data_url` 必须 `data:image/*;base64,` 且 ≤ 8 MiB；**图片校验失败会把这轮的 id 判死**，用户改图重试要换新 id。
6. `reasoning_level` 控件在 cloud 下隐藏或置灰。
7. `voice_attempted` 默认为真：若不想每轮都被桌宠念，需要后端/设置侧关 `voice_enabled`（前端无法单独抑制）。
