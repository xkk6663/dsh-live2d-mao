# 项目独立性技术分析：Electron 运行时目录与 ACL 权限

> 版本：v2 ｜ 2026-10-19 ｜ 状态：**方案 B 已实施（见第九节）**
> 适用：`dsh-live2d-mao` 仓库（DSH 专用 Live2D 桌宠）
> 结论先行：**当前桌宠能跑，但依赖仓库目录上一条"从上游复制继承来的" ACL 规则。
> 换机器/换目录 clone 必然失败。修复方案 = 在安装阶段主动补齐权限（方案 B）。**

---

## 一、问题陈述

用户要求：**本项目必须完全独立** —— 单独 clone/下载本仓库，不依赖任何其它仓库或项目，就能跑起来。

当前状态：**不满足**。

| 场景 | 结果 |
|---|---|
| 在本机（`C:\Users\xiao1\Mao-dsh-pet`）运行 | ✅ 能跑 |
| 换一台机器 / 换一个目录 clone | ❌ **必然失败**（Electron 秒退） |

---

## 二、技术难点（三层，逐层剥开才定位到真根因）

### 难点 1：Electron 进程跑在 AppContainer 沙箱里

本机 Electron 子进程（由 DSH 宿主环境启动链继承）运行在 **AppContainer** 上下文中，
对绝大多数路径的 `mkdir` / `write` 均被拒绝：

| 目标目录 | 实测结果 |
|---|---|
| 项目根 `pet-data\…` | `Error 5`（拒绝访问） |
| `%TEMP%\…` | `Error 5` |
| `%LOCALAPPDATA%\…` | `EPERM`（弹出 "A JavaScript error occurred in the main process"） |
| 项目根（有 ACL 规则时） | ✅ 可用 |

**推论**：不是"某条路径不对"，而是**权限模型**问题 —— 只有被显式授权的目录可写。

### 难点 2：真根因是仓库目录上的一条继承 ACL

逐级追溯 ACL，发现关键事实：

```
C:\                         : 无 SID 规则
C:\Users                    : 无
C:\Users\xiao1              : 无
C:\Users\xiao1\Mao-dsh-pet  : ★ 有显式规则（本仓库根）
C:\Users\xiao1\Mao-dsh-pet\pet-data            : 继承
C:\Users\xiao1\Mao-dsh-pet\pet-data\pet-instance : 继承
```

仓库根 `Mao-dsh-pet` 上的两条**显式**规则：

| 主体 | 权限 | 类型 |
|---|---|---|
| `Everyone` | `DeleteSubdirectoriesAndFiles` | **Deny** |
| `S-1-4-49512934-974561200`（AppContainer SID） | `Write, Delete, DeleteSubdirectoriesAndFiles, Synchronize` | **Allow** |

对比上游 `C:\Users\xiao1\Mao` 仓库根：**DACL 完全相同**。

> ❌ **更正（2026-10-19 实测推翻）**：当时用 `Get-Acl` 对比，**只读了 DACL，漏读了 SACL**。
> 用 `icacls` 看完整安全描述符会发现上游多一行：
>
> ```
> C:\Users\xiao1\Mao          … Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)   ← 上游有
> C:\Users\xiao1\Mao-dsh-pet  … （无此行）                                        ← 本仓库没有
> ```
>
> **这一行才是"桌宠起不来"的真根因**（详见 §十一）。它决定 Electron（Low IL）
> 能不能往这个目录写，DACL 再宽松也救不了。

**结论**：这两条 DACL 规则是**从上游 Mao 仓库复制/克隆时继承下来的**，
本仓库「碰巧」继承了它，所以 Electron 在 `pet-data` 下能建单实例锁。

> ⚠️ 也就是说：**当前"能跑"是历史遗留的巧合，不是设计**。

### 难点 3：Chromium 的两个目录都可能被拒

Electron 需要两个运行时目录，权限要求不同：

| 目录 | 作用 | 当前设置 | 实测 |
|---|---|---|---|
| `userData`（`INSTANCE_DIR`） | 单实例锁 `SingletonLock` | `pet-data\pet-instance` | ✅ 可用（因为有那条 ACL） |
| `sessionData` | Chromium 缓存 / 网络上下文 / LocalStorage | `pet-data\Live2D桌宠\Chromium` | ⚠️ **`Network` / `Code Cache` 子目录仍被拒**（0x5），但主窗口能开 |

日志证据：

```
Failed to create network context data directory
  C:\...\pet-data\Live2D桌宠\Chromium\Network: 拒绝访问。(0x5)
Failed to create directory: ...\Chromium\Code Cache\js
```

> 影响：主功能正常，但**离线缓存/网络栈受限**，长期可能影响音频/图片加载性能。
>
> ✅ **2026-10-19 已解决**：根因同样是缺 `Low` 完整性标签。补上之后
> `Network` / `Code Cache` / `GPUCache` 全部正常建出（详见 §十一）。

## 四、解决方案（方案 B：安装阶段补权限）

### 4.1 核心思路

**权限问题必须在"有完整权限的上下文"里解决**。

- 运行期（Electron / AppContainer）：权限受限，改不了 ACL ⇒ **不能在这里修**
- 安装期（用户手动运行 `安装依赖.ps1`）：**正常用户权限** ⇒ **在这里授权**

安装脚本本来就要用户跑一次（装 Python/Node/Electron），
在里面加一步 ACL 授权，**零额外操作成本**。

### 4.2 具体改动

#### 改动 1：`安装依赖.ps1` 新增「第 5 步：准备运行时目录」

```
[5/5] 准备桌宠运行时目录（解决换机权限问题）...
```

做的事：
1. 创建 `pet-data\pet-instance` 与 `pet-data\Live2D桌宠\Chromium`
2. **移除 Everyone 的 Deny 规则**（继承来的，会阻碍写入）
3. 授予以下主体 `(OI)(CI)F` 完全控制：
   - 当前用户（`$env:USERNAME`）
   - `Everyone`（覆盖 AppContainer 场景）
   - **AppContainer SID**（若 `pet-data` 上已存在同类规则，复用它）
4. 写一个探测文件验证真的可写；失败则**明确报错并给出修复命令**（不静默通过）

#### 改动 2：`main.js` 兜底自检

在 `setPath` 之前加一个**只读检查**（不改 ACL，只判断）：
- 尝试在 `INSTANCE_DIR` 建探测文件
- 成功 → 正常启动
- 失败 → 记录明确日志（含"请运行 安装依赖.ps1"指引），并尝试 `%TEMP%` 兜底

> 为什么不在 main.js 里改 ACL：AppContainer 下 `icacls` 同样被拒（本机实测），
> 写了也没用，只会让代码更复杂。

#### 改动 3：`start_mio.ps1` / `restart_mio.ps1` 启动前预检

启动 Electron 前，检查 `pet-data\pet-instance` 是否可写：
- 可写 → 继续
- 不可写 → 打印清晰指引：`请先运行 安装依赖.ps1`，并**不启动**（避免秒退后用户困惑）

### 4.3 为什么选 B 而不是其它方案

| 方案 | 做法 | 评价 |
|---|---|---|
| A 配置化 | instance 目录做成配置项，多级探测 | ❌ 治标：换机器仍然没权限，只是报错更晚 |
| **B 安装阶段授权** | **安装脚本补 ACL** | ✅ **推荐**：零额外成本、真正独立、换机器可跑 |
| C 命令行绕开 | `--user-data-dir` 指定目录 | ⚠️ 仍需目录可写，权限问题没解决；可作为 B 的补充 |
| D 改到系统标准目录 | `%APPDATA%` / `%LOCALAPPDATA%` | ❌ 本机实测 `EPERM`，且 AppContainer 下同样受限 |

### 4.4 预期效果

| 场景 | 修复后 |
|---|---|
| 本机 | ✅ 正常（且不再依赖继承来的 ACL） |
| 新机器 clone + 跑安装脚本 | ✅ 正常 |
| 新机器 clone 但**没**跑安装脚本 | ⚠️ 明确报错并提示跑安装脚本（不静默秒退） |

## 五、待确认的未知项（实施前必须验证）

### 未知 1（已部分解决）：AppContainer SID 是固定的吗？

**已验证的事实**：

| 验证项 | 结果 |
|---|---|
| 是否由 electron.exe 路径哈希派生 | ❌ 不是（路径 MD5/SHA256 前 16 位均不匹配 SID 的 0x02f381e63a169fb0） |
| 系统是否有注册的 AppContainer 包 | ❌ 无（`Get-AppxPackage` 查不到 electron/Mio/DSH 相关包） |
| 该 SID 规则出现在哪些目录 | **仅 `Mao` 与 `Mao-dsh-pet` 两个仓库根**，其它用户目录都没有 |
| 是否是继承还是显式 | 两个仓库根都是**显式**规则（`IsInherited: False`） |

**结论**：这条规则是**手工加过 / 复制目录时带过来的**，不是系统自动生成。
⇒ 换机器**大概率没有**，安装脚本必须主动添加。
⇒ SID 值需**动态获取**（不能硬编码）：优先从已有目录 ACL 反查，其次 `whoami`，最后 Everyone 兜底。

### 未知 2（仍未解决，需你配合）：沙箱限制是"本会话特有"还是"通用"？

**已排除的解释**：
- ❌ 不是"普通用户权限不足" —— 我的会话是 Medium Integrity 普通用户，能正常写 `pet-data`
- ❌ 不是那条 `Everyone: Deny DeleteSubdirectoriesAndFiles` —— 实测我当前会话建子目录/删文件都正常
- ⚠️ electron 进程 owner 也是 `xwk`（普通用户），**不是 AppContainer 服务账户**

**当前判断**：写入失败**只在 Electron 子进程内发生**，而非整个会话。
可能是 Electron 自身的 Chromium 沙箱（`--no-sandbox` 未完全关闭某些限制），
也可能是 DSH 宿主注入的环境变量（如 `ELECTRON_RUN_AS_NODE` 之类的继承链）导致。

**必须由你在干净环境验证**（我在 DSH 会话里测不出真相）：

```powershell

taskkill /F /IM electron.exe

# 2. 打开一个【普通 cmd 窗口】（开始菜单搜 cmd，不要用 DSH 的终端）

# 3. 在新窗口里手动跑
cd C:\Users\xiao1\Mao-dsh-pet\澪Agent应用\live2d-desktop

# 4. 观察是否仍报 "Lock file can not be created! Error code: 5"
```

| 观察结果 | 含义 | 方案 B 是否必要 |
|---|---|---|
| **干净 cmd 里能启动** | 限制是本 DSH 会话特有 | 方案 B 降级为防御性措施（仍建议做，成本低） |
| **干净 cmd 里也报 Error 5** | 是机器/Electron 版本问题 | **方案 B 必须做**，且要按本文档第 4 节实施 |

### 9.2 关键设计决策（与最初设想不同之处）

**① ACL 用「断开继承 + 重建」而不是「删掉那条 Deny」**

最初的设想是只移除 `Everyone: Deny DeleteSubdirectoriesAndFiles`。
实施时改成更强的做法：**断开继承**，让 `pet-data` 的权限**自包含** ——
这才是"项目完全独立"的字面含义（删掉一条继承 ACE，下次仍可能有别的继承规则来捣乱）。

最终工具链是 **`icacls` 为主 + `.NET` 补一条 SID 规则**（中间踩了两个坑，见 9.4）：

```powershell
# 主路径：icacls（幂等，可反复运行；/inheritance:r 断开继承并丢弃继承 ACE）
icacls $d /inheritance:r /remove:d Everyone `
       /grant:r "$me:(OI)(CI)F" /grant:r "SYSTEM:(OI)(CI)F" `
       /grant:r "Administrators:(OI)(CI)F" /grant:r "Everyone:(OI)(CI)M"
```

`Everyone` 只给 `Modify`（不含 `WRITE_DAC`），比原来的 `FullControl` 更保守。

**② AppContainer SID 改为「探测到才复用」，不再强求**

原文档要求"动态获取 SID"。实施时发现：新机器上根本没有这个 SID 可供反查
（它只存在于两个老仓库根的显式 ACL 里）。而普通用户从资源管理器双击启动时，
Electron **不在** AppContainer 里，根本不需要这条规则。
故策略改为：**能探测到就复用，探测不到就跳过**——不硬编码、不伪造。

**③ 全不可写时 main.js 仍继续尝试启动，启动脚本则中止**

`main.js` 里探针失败时弹窗但**不 abort**：`dialog.showErrorBox` 是同步 MessageBox，
用户一定能看见；且某些受限下探针会误报失败，而 electron 自己的锁反而能建；
直接 `app.exit()` 会让用户连"弹窗 + 日志"都拿不到。

启动脚本层相反：`start_mio.ps1` / `restart_mio.ps1` 探测全失败会 `Exit(1)`，
因为脚本层退出不丢窗口，反而避免"拉起 → 秒退 → 用户困惑"。

### 9.4 两个真 Bug：SID 不能按名字翻译 / Set-Acl 对已保护 DACL 必失败

**Bug 1 · AppContainer SID 不能按名字构造 ACL 规则**

第一次真跑安装脚本时，四个目录全部报：

```
AddAccessRule 时发生异常：「未能转换部分或所有标识引用。」
```

原因：`New-Object FileSystemAccessRule('S-1-4-49512934-974561200', ...)` 传的是**字符串**，
.NET 会先尝试把名字翻译成 SID —— 而 AppContainer SID **没有对应名字**，翻译必失败。
临时目录干跑时之所以没暴露，正是因为那里探测不到 AppContainer SID（走了纯名字分支）。

修法：SID 字符串直接 `new SecurityIdentifier()`，名字走 `NTAccount.Translate()`：

```powershell
if ($id -match '^S-1-\d') { return New-Object System.Security.Principal.SecurityIdentifier($id) }
$nt = New-Object System.Security.Principal.NTAccount($id)
return $nt.Translate([System.Security.Principal.SecurityIdentifier])
```

**Bug 2 · `Set-Acl` 对「已经是保护状态」的 DACL 稳定失败**

修完 Bug 1 后第二次运行时四个目录全报：

```
该进程不具有执行此操作所需的 SeSecurityPrivilege 特权。
```

复现实验（临时目录，与项目无关）：

| 操作 | 结果 |
|---|---|
| 对未保护的目录 `SetAccessRuleProtection($true,$false)` + `Set-Acl` | ✅ 成功 |
| **同一目录再跑一遍**同样的调用 | ❌ `SeSecurityPrivilege` |
| 之后连"取消保护"（`SetAccessRuleProtection($false,$true)`）| ❌ 同样失败 |
| 对已保护目录改用 `icacls /inheritance:r /grant:r ...` | ✅ 成功，且反复运行都成功 |

⇒ 结论：**`Set-Acl` 只能用于"第一次"**，幂等性完全坏掉；`icacls` 才是可重入的正路。

但 `icacls` **不认 SID 字符串**：

```
icacls ... /grant:r "*S-1-4-49512934-974561200:(OI)(CI)F"
→ 账户名与安全标识间无任何映射完成。（exit 1332）
```

所以最终分工：

| 步骤 | 工具 | 做什么 | 何时 |
|---|---|---|---|
| A | `.NET`（`Set-Acl`） | **只**给 AppContainer SID 补一条显式 FullControl | 仅当 ACL 尚未保护、且 SID 规则缺失（即首次在这台机器上授权） |
| B | `icacls` | `/inheritance:r` 断继承 + `/remove:d Everyone` + 四条 `/grant:r` | **每次都跑**（幂等） |

> 教训补一条：**干跑样本必须覆盖"分支的每一侧"**。
> 临时目录里没有 AppContainer SID，等于只测了"没有 SID"那条路；
> 而"第一次能过、第二次必挂"这类**幂等性**问题，也只有**连跑两次**才会现形。
> 本轮的验收标准因此改成：**安装脚本必须能连续跑两次都全绿**。

## 十一、★ 真根因更正：完整性标签（Low Mandatory Level）

> **时间**：2026-10-19 10:50，改造完成后用户实际双击启动，弹窗：
> 「Mao-pet 启动失败：运行时目录不可写 / `...\pet-data\pet-instance`」
> 而 5 分钟前刚验证过：DACL 全对、普通 PowerShell 写删都正常、安装脚本连跑两次全绿。
> **说明前九节的分析在"权限模型"上还差最后一层。**

### 11.1 决定性对照实验

同一个目录，两种身份，结论相反：

| 身份 | 操作 | 结果 |
|---|---|---|
| 普通进程（Medium IL，`icacls` / PowerShell / bash） | 在 `pet-instance` 建文件 + 删除 | ✅ 成功 |
| **Electron（Low IL / AppContainer）** | 同样操作 | ❌ `EPERM`，连 `SingletonLock` 都没建出来 |

`pet-instance` 里**没有留下探针文件** ⇒ 失败点在 `mkdir`/`write`，不在 `unlink`；
ACL 逐条看又是全开的 ⇒ **不是 DACL 的事**。

### 11.2 用 `icacls` 看完整安全描述符（`Get-Acl` 看不到这一层）

```
C:\Users\xiao1\Mao                       → Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)   ✅
C:\Users\xiao1\Mao\pet-data              → Mandatory Label\Low Mandatory Level:(I)(OI)(CI)(NW)（继承）
C:\Users\xiao1\Mao\pet-data\pet-instance → Mandatory Label\Low Mandatory Level:(I)(OI)(CI)(NW)（继承）
C:\Users\xiao1\Mao-dsh-pet               → （无 Mandatory Label 行）                            ❌
```

**根因**：Electron 被降权到 **Low 完整性级别** 运行。Windows 的强制完整性控制（MIC）规定
**Low 进程不能"向上写" Medium 对象**（no-write-up），这条策略**优先于 DACL** ——
所以把 Everyone/当前用户/AppContainer SID 全给 FullControl 也没用。

上游 `Mao` 之所以能跑，靠的就是根目录上那行 `Low Mandatory Level:(OI)(CI)(NW)`，
子目录一路继承。本仓库 clone/复制时**没有带上它**（SACL 不随 git 走，也不随普通复制走），
于是 `pet-data` 是隐式 Medium ⇒ Electron 写不进去。

> 这也解释了为什么 `安装依赖.ps1` 第一次跑"成功"却启动失败：
> 探针是 **Medium 进程**跑的，"Medium 能写"和"Low 能写"是两件事。

### 11.3 修法

```powershell
icacls "C:\Users\xiao1\Mao-dsh-pet\pet-data" /setintegritylevel (OI)(CI)Low /T
```

- 非提权即可执行（实测 `exit=0`），产出正是 `Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)`
- `/T` 让**已存在**的子项（`pet-instance` / `Live2D桌宠` / `Chromium` / `models` / `runtime.json` …）一起带上
- `(OI)(CI)` 保证**将来**新建的子项继承
- 安全性影响：Low 标签只挡"向上写"，Medium 的后端/脚本**照常读写**（write-down 允许），
  代价是"同机其它低完整性进程也能写这个目录"——与上游仓库既有做法一致

> **给后来者的教训（三条，按重要性排序）**
> 1. **`Get-Acl` 只读 DACL**。要判断"能不能写"必须连**完整性标签**一起看，用 `icacls`。
> 2. **"我这边能写"不等于"Electron 能写"**。降权进程的写入能力必须用**同等身份**验证。
> 3. "两个目录 ACL 完全相同"这种结论，只要工具少读一个分量就是错的 —— **别用单一 API 下结论**。
